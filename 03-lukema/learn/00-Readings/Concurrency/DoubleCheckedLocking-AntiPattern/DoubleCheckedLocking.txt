
Double-Checked Locking, or double-checked locking optimization: 

to reduce the overhead of acquiring a lock by first testing the locking 
criterion (the 'lock hint') in an unsafe manner; only if that succeeds 
does the actual lock proceed.

The pattern, when implemented in some language/hardware combinations, 
can be unsafe. It can therefore sometimes be considered to be an anti-pattern.

It is typically used to reduce locking overhead when implementing "lazy 
initialization" in a multi-threaded environment, especially as part of the 
Singleton pattern. 

One of the dangers of using double-checked locking in J2SE 1.4 
(and earlier versions) is that it will often appear to work: it is not 
easy to distinguish between a correct implementation of the 
technique and one that has subtle problems.

As of J2SE 5.0, this problem has been fixed. The volatile keyword now 
ensures that multiple threads handle the singleton instance correctly.
